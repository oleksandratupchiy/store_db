# Лабораторна №2: NoSQL для магазину

## Мета й типи NoSQL

Побудувати модель читання завершених замовлень, порівняти її з нормалізованою
реляційною моделлю та продемонструвати key-value кеш і рейтинг товарів.

| Тип | Організація і призначення | Приклади |
|---|---|---|
| Document | Вкладені документи; каталог, історія замовлень, гнучкі атрибути | MongoDB, Couchbase |
| Key-value | Доступ за ключем; кеш, сесії, лічильники | Redis, Amazon DynamoDB (key-value/document) |
| Wide-column | Рядки з сімействами колонок; великі розподілені часові потоки | Cassandra, HBase |
| Graph | Вершини й ребра; зв'язки, рекомендації, маршрути | Neo4j, JanusGraph |

NoSQL не означає відсутності схеми чи будь-яких транзакцій. Модель вибирають під запити.

## Вибір для магазину

PostgreSQL залишається джерелом істини: транзакційне оформлення покупки, оплата,
склад і FK-обмеження. MongoDB містить денормалізовану історію для читання:
одне замовлення разом із покупцем, позиціями й платежами отримується без JOIN.
Це зменшує кількість звернень для конкретного сценарію, але дублює дані,
потребує додаткового диска, індексів та синхронізації. Жодних висновків про
універсальну перевагу MongoDB з цього експерименту робити не можна.

V1/V2 не містять статусу завершення. Лабораторне правило: `total_amount > 0`,
є хоча б одна позиція, `SUM(payment.amount) >= total_amount`.
Воно однакове для SQL-вибірок та імпорту. Це наближення до «завершеного»,
а не ознака відвантаження. У виробничій системі потрібні статус і події оплати.

Імпорт — batch snapshot у repeatable-read read-only транзакції PostgreSQL,
заміна документів через upsert за `_id`. Повторний запуск не створює дублікатів.
Перерваний імпорт можна повторити. Видалення/відкликання оплати не поширюються
автоматично: старі Mongo документи не видаляються. Для виробничої синхронізації
можна використати transactional outbox/CDC, повторювані події, tombstone та моніторинг відставання.

## Документ і SQL-мапінг

Приклад **схеми**, не результат вимірювання:

```javascript
{
  _id: 1,
  customer: {id: 1, name: 'Customer 1'},
  employee_id: 1,
  order_date: ISODate('2025-01-01T12:00:00Z'),
  total_amount: NumberDecimal('120.00'),
  items: [{id: 1, product_id: 1, name: 'Coffee', quantity: 1,
           unit_price: NumberDecimal('120.00')}],
  payments: [{id: 1, method: 'CARD', amount: NumberDecimal('120.00'),
              date: ISODate('2025-01-01T12:01:00Z')}]
}
```

| SQL таблиця | Поля документа |
|---|---|
| `sales_order` | `_id`, `employee_id`, `order_date`, `total_amount` |
| `customer` (LEFT JOIN) | `customer.id`, `customer.name` |
| `sales_order_item` + `product` | `items[]`, ціна з `unit_price`, назва з `product.name` |
| `payment` | `payments[]` |

**Назва товару — поточний знімок під час імпорту**, а не назва на момент купівлі:
у першій лабораторній історична назва не зберігається. `unit_price` є ціною продажу.
ПІБ покупця також копіюється на момент імпорту. Decimal128 використовується замість double;
гроші нормалізуються через `stripTrailingZeros()`. TIMESTAMP WITHOUT TIME ZONE
інтерпретується як UTC wall-clock; Mongo BSON Date має точність мілісекунд,
зайві мікросекунди відкидаються. Це домовленість лабораторної, не автоматичне
визначення часового поясу старих даних. Генератор створює цілі секунди та суми до копійки.

SQL повертає заголовки одним запитом, позиції всіх обраних замовлень другим,
платежі третім (`IN` для вибраних ID). Java складає `Document` тієї самої структури,
яку повертає Mongo. Позиції й платежі впорядковані за своїм ID.
Немає декартового множення `items × payments`, N+1 або JSONB-таблиці.

## Запити

Фрагменти SQL (повна реалізація `History.Sql`):

```sql
-- До всіх запитів додається однаковий критерій завершення:
SELECT o.id, o.employee_id, o.order_date, o.total_amount, c.id, c.full_name
FROM sales_order o LEFT JOIN customer c ON c.id=o.customer_id
WHERE o.total_amount>0
  AND EXISTS (SELECT 1 FROM sales_order_item i WHERE i.sales_order_id=o.id)
  AND (SELECT COALESCE(SUM(p.amount),0) FROM payment p
       WHERE p.sales_order_id=o.id)>=o.total_amount
  AND o.id = :id;
-- Останні замовлення: AND o.customer_id=:customer
-- ORDER BY o.order_date DESC, o.id DESC LIMIT 20
-- Дати: AND o.order_date>=:from AND o.order_date<:to
-- ORDER BY o.order_date DESC, o.id DESC LIMIT 20
SELECT i.*,p.name FROM sales_order_item i LEFT JOIN product p ON p.id=i.product_id
WHERE i.sales_order_id IN (:selected_ids) ORDER BY i.id;
SELECT * FROM payment WHERE sales_order_id IN (:selected_ids) ORDER BY id;
-- Статистика: COUNT(*), COALESCE(SUM(o.total_amount),0)
-- з тим самим WHERE завершення AND o.customer_id=:customer.
```

MongoDB (`use lab2_n1000_s42`):

```javascript
db.order_history.find({_id: 1})
db.order_history.find({'customer.id': 1}).sort({order_date:-1,_id:-1}).limit(20)
db.order_history.find({order_date: {$gte:ISODate('2025-01-01'), $lt:ISODate('2025-02-01')}})
  .sort({order_date:-1,_id:-1}).limit(20)
db.order_history.aggregate([
  {$match:{'customer.id':1}},
  {$group:{_id:null,count:{$sum:1},total:{$sum:'$total_amount'}}}
])
db.order_history.getIndexes()
```

Вставка й оновлення: `scripts/mongo-demo.js` виконує upsert `$setOnInsert`, потім
`$set`, у **окремій** `lab2_demo.order_history`, ID -1. Робоча модель імпорту
використовує bulk `replaceOne` із `upsert=true`.

Індекси Mongo: вбудований `_id`; `{customer.id:1, order_date:-1, _id:-1}`
для покупця та останніх замовлень; `{order_date:-1,_id:-1}` для діапазону й сортування.
SQL V3: аналогічні B-tree на `(customer_id,order_date DESC,id DESC)` та
`(order_date DESC,id DESC)`, плюс індекси FK `sales_order_item(sales_order_id,id)`
і `payment(sales_order_id,id)` для завантаження дочірніх записів/критерію оплати.
Індекси не безкоштовні: збільшують місце та вартість запису.

## Генератор і методика

Параметри: count і seed. Окрема БД `store_db_benchmark`, окрема схема на count/seed;
V1/V2 без змін і V3 з індексами застосовуються Flyway. Створюються всі потрібні FK:
магазин, відділ, роль, працівник, категорія, 100 товарів, покупці, замовлення, позиції,
платежі. Решта необов'язкових таблиць залишається порожньою. На замовлення 3–7
позицій (середнє близько 5), кількість 1–3, детерміновані ціни, дата протягом 2025 року.
Кожне третє замовлення має два платежі; їх сума точно дорівнює сумі позицій.
Mongo отримує дані **з PostgreSQL**, тому немає двох незалежних генераторів.
Повторна генерація непорожнього набору заборонена; жодного TRUNCATE/DROP немає.

100 замовлень — smoke; 1 000, 10 000, 100 000 демонструють зміну порядку масштабу
та приблизно 5 000, 50 000, 500 000 позицій. Кількість покупців `max(10,count/100)`:
історія одного покупця приблизно 100 замовлень на кожному масштабі, що слід
враховувати при тлумаченні клієнтського сценарію. Це синтетичний, а не реальний розподіл продажів.

`Benchmark` працює без HTTP. JDBC-з'єднання і MongoClient відкриті до замірів;
SQL read-only repeatable-read snapshot, дані Mongo під час вимірювань не змінюються.
Перед benchmark перевіряється кількість документів та рівність 20 зразків кожного
з чотирьох сценаріїв, відсутнього ID і покупця. Помилка зупиняє запуск до запису CSV.
Перевірки не є доказом рівності кожного документа, але виявляють типові помилки мапінгу.

Сценарії: ID; останні 20 замовлень покупця; напіввідкритий діапазон 30 днів із лімітом
20; кількість і сума завершених замовлень покупця. Псевдовипадкова послідовність запитів
визначається seed, однакова для обох БД. Default: 50 прогрівів та 200 вимірювань
на сценарій/БД; цього достатньо для навчального p95, але для стабільних висновків
потрібні незалежні повторні запуски. Порядок SQL/Mongo чергується на кожній ітерації.

Повторні серії запускаються послідовно через `scripts/benchmark.ps1 -Reuse`.
Кожний виклик створює новий JVM-процес; усередині серії масштаби йдуть у порядку
1 000 → 10 000 → 100 000. Seed=42 залишає однаковими дані та послідовність запитів.
«Незалежна серія» тут означає окремий запуск програми, а не новий випадковий набір
чи гарантовану статистичну незалежність: БД і ресурси машини спільні.

Використовуються **прогріті кеші**: кеші ОС/БД не очищуються, контейнери між серіями
не перезапускаються. Підготовка даних, перевірки та 50 прогрівів впливають на кеші;
їх точне наповнення не фіксується. Наявний `-Reuse` пропускає генератор, але повторно
імпортує дані в MongoDB через upsert перед кожним масштабом. Це додатково прогріває
читання PostgreSQL і записи/індекси MongoDB. **Час імпорту не входить у benchmark**,
як і відкриття з'єднань, створення індексів та звірка результатів. SQL і MongoDB
порівнюються як дві моделі читання з однаковим логічним результатом: нормалізовані
таблиці з перевіркою оплати під час читання та заздалегідь зібрані завершені замовлення.

`System.nanoTime()` охоплює виконання, мережу, читання курсорів і складання порівнянного
результату. Значення зберігається у volatile sink. Не вимірюється відкриття з'єднань,
створення індексів, генерація, імпорт чи перевірка рівності. Медіана й p95 — nearest-rank
`ceil(p*n)-1` у відсортованому масиві; також обчислюється арифметичне середнє; одиниця CSV — ms.
Сирі виміри кожної ітерації не зберігаються; CSV містить агрегати одного запуску.
Статистика рахується БД без повернення всіх замовлень у Java.

Форма CSV (лише заголовок, жодних вигаданих чисел):

```csv
timestamp_utc,orders,seed,scenario,store,warmup,repetitions,median_ms,p95_ms,mean_ms
```

Графіки SVG будує `python scripts/plot_results.py` тільки з `benchmark_*.csv`.
Для кожного сценарію своя лінійна шкала, підписи в мілісекундах. Стовпчики показують
середні медіан (`median_ms.svg`) або середні p95 окремих запусків (`p95_ms.svg`);
вуса — фактичні min–max між запусками, n — кількість запусків. На smoke з n=1 вусів
немає. Середнє p95 не є p95 об'єднаних операцій. Без реальних CSV скрипт відмовляється
створювати графіки.

Обмеження: теплі кеші ОС/БД, JIT і GC JVM; Docker VM, CPU/RAM та фонове навантаження;
мережеві round trips (SQL має три запити для повного документа); різний фізичний
обсяг денормалізованих документів; відсутність конкурентних записів та реплікації.
Підготовка й імпорт уже прогрівають кеш. Це порівняння реалізованих моделей читання,
а не ізольованих SQL execution plans чи граничної пропускної здатності серверів.

## Redis: key-value та sorted set

`scripts/redis-demo.ps1` використовує лише Redis цього Compose і логічну БД 15,
зарезервовану для лабораторної. Паролі/продуктивні кеші сюди не підключаються.

```text
SELECT 15
SET product:1 '{"name":"Coffee","price":"120.00"}'
GET product:1
EXISTS product:1
SET product:1 '{"name":"Coffee","price":"125.00"}'
EXPIRE product:1 120
TTL product:1
DEL product:1
EXISTS product:1
ZADD popular_products 12 Coffee 8 Tea 5 Chocolate
ZINCRBY popular_products 3 Tea
ZRANGE popular_products 0 9 REV WITHSCORES
```

SET створює/оновлює кеш, GET читає, DEL видаляє, EXPIRE обмежує час життя.
Score рейтингу — навчальна кількість проданих одиниць: Coffee 12, Tea 11,
Chocolate 5 після додаткових трьох продажів чаю. ZADD спочатку встановлює
фіксовані оцінки, тому повторний запуск відтворюваний. Це окремі демонстраційні
дані, не автоматичне відображення згенерованих продажів PostgreSQL.
Redis в цьому завданні не є джерелом істини.

Повторна перевірка демо після виправлення сумісності з **Windows PowerShell
5.1.26100.9818** підтвердила успішний запуск обох скриптів з кодом 0.
Причина попереднього `ERR unknown command`: `ValueFromRemainingArguments` отримував
розгорнутий масив як один рядок (`EXPIRE product:1 120`). Виклики виправлено на
явний іменований масив `-RedisArgs @(...)`, який передається Docker через splatting.
`redis-cli -e` забезпечує ненульовий код для помилки сервера; додатково перевіряється
відповідь `ERR`, навіть якщо обгортка повернула 0. Помилки Docker також зупиняють демо.
Новий фактичний вивід збережений у `testing/results/redis-demo.txt`:
усі 11 команд виконані без ERR, рейтинг Coffee 12, Tea 11, Chocolate 5.

Окремий запуск `mongo-demo.ps1` завершився `Mongo demo PASS`, без Redis/ZRANGE у
виводі (`testing/results/mongo-demo.txt`). Цей скрипт виконує тільки `compose cp`
та запуск Mongo shell у сервісі `mongo`; Redis він не викликає. Походження старого
змішаного термінального виводу без його журналу точно встановити неможливо.
Mongo-демо перевіряє підтвердження записів і результат оновлення, а JavaScript
помилку завершує через `quit(1)`; PowerShell перевіряє коди копіювання і shell.

Перевірка передачі всіх аргументів і сценаріїв відмов без сервісів:
`powershell.exe -NoProfile -File testing/check-demo-scripts.ps1`.
Вона використовує підміну Docker тільки в окремих дочірніх процесах Windows PowerShell.

## Фактичні результати

Виконано 10.11.2026: три серії на основних наборах 1 000 / 10 000 / 100 000
замовлень (9 проходів benchmark) та окремий smoke на 100 замовлень.
Seed=42, 50 прогрівів, 200 вимірювань на операцію/БД у кожному проході.
Усі перевірки еквівалентності пройшли. SQL-перевірка всіх сум у трьох основних
наборах дала `invalid_totals=0`; найбільший набір має 500 648 позицій і 133 333 платежі.
Повна регресія в окремій схемі тестової БД: 9 тестів пройдено, без помилок і пропусків.
Redis CRUD/TTL/рейтинг, Mongo insert/update та побудова обох графіків виконані успішно.

Середовище: Windows 11, Oracle JDK 25 (компіляція `--release 17`),
PostgreSQL 17.11, MongoDB **4.4.29**, Java driver 5.8.1, Redis 7.4.12;
Docker Engine 29.9.2, WSL2 x86_64, 4 vCPU і приблизно 7.66 GiB RAM для Docker.
MongoDB 8.0 на цій Docker VM завершилася з кодом 132 через відсутність AVX:
для фактичного експерименту застосовано `docker-compose.noavx.yml` з окремим volume.
MongoDB 4.4 — застарілий локальний навчальний варіант. Швидкодію MongoDB 8 тут
**не виміряно**; переносити наведені числа на неї не можна.

Затримки у мілісекундах, округлені до 3 знаків; повна точність, середнє та UTC-час
запуску збережені у [CSV](../testing/results/). Нижче наведені метрики **першої серії**:
медіана й p95 обчислені всередині одного запуску з 200 вимірювань.

ті самі PostgreSQL/MongoDB і дані. Генератор не запускався, SQL не змінювався.
Контейнери PostgreSQL і MongoDB запущені о 10:23:24 і 10:33:16 UTC відповідно —
до першої серії. Їхні ID, StartedAt і RestartCount=0 не змінилися до завершення
повторів: контейнерів між серіями не перезапускали. Параметри, часові межі,
перелік шести нових CSV та знімки стану — у
[`repeated_series_manifest.json`](../testing/results/repeated_series_manifest.json).

Нехай mᵢ — медіана 200 операцій у запуску i. У таблиці середнє медіан
`m̄ = sum(mᵢ)/n`, вибіркове стандартне відхилення
`s = sqrt(sum((mᵢ−m̄)²)/(n−1))` і min/max серед mᵢ; n=3.
Це **мінливість медіан між запусками**, а не середнє `mean_ms` окремого запуску,
не стандартне відхилення 600 операцій і не об'єднаний p95. Сирі 200 спостережень
не збережені, тому відновити об'єднану медіану чи p95 із цих CSV неможливо.
Кожний запуск має однакову вагу. Усі валідні CSV включено; жодних викидів не вилучено.
Smoke на 100 замовлень теж проаналізовано в окремих рядках зведеного CSV:
n=1, вибіркове s не визначене (порожнє поле); у таблицю основних масштабів він не входить.

## Висновки та запитання на захисті

Реалізовано два різні NoSQL-підходи: документна модель історії й key-value кеш
із рейтингом. Нормалізована PostgreSQL-модель зберігає цілісність транзакцій;
MongoDB спрощує читання повного замовлення ціною дублювання та синхронізації.
У трьох фактичних серіях середні медіан повного читання нижчі у MongoDB;
агрегатна статистика дає близькі результати. Значний міжзапусковий розкид вимагає
обережного тлумачення; висновки стосуються цих моделей читання та середовища.

1. **Чому MongoDB не замінює PostgreSQL?** Склад, оплата й покупка потребують
   узгоджених транзакцій; нова колекція — похідна модель читання.
2. **Навіщо вкладені масиви?** Позиції й платежі читаються разом із замовленням;
   у цієї моделі обмежений розмір. Дуже великі замовлення треба розбивати з огляду
   на ліміт BSON-документа MongoDB.
3. **Чи назва товару історична?** Ні, вона взята під час імпорту; ціна продажу —
   історична з `sales_order_item.unit_price`.
4. **Як уникнути дублікатів і розбіжностей?** `_id` дорівнює PK, upsert і повторний імпорт;
   для онлайн-системи — outbox/CDC, ідемпотентність і контроль відставання.
5. **Чи порівняння чесне?** Однакові логічні дані, фільтри, порядок, ліміти, прогрів
   і матеріалізація; індекси є в обох БД. Фізичні моделі й число round trips різні,
   це частина предмета порівняння.
6. **Чому p95, а не тільки середнє?** Воно показує затримку верхнього хвоста;
   середнє чутливе до одиничних пауз JVM/ОС. Для оцінки мінливості повторюємо запуски.
7. **Чому не JOIN усіх п'яти таблиць одразу?** Дві позиції й два платежі дадуть чотири
   рядки; окремі пакетні запити зберігають правильну кратність і суми.
8. **Для чого Redis sorted set?** Він підтримує зміну лічильника продажів і отримання
   top-N без сортування всього каталогу в клієнті; TTL корисний для звичайного кешу.
